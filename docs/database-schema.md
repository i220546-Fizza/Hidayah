# Database schema

PostgreSQL 16 with the pgvector extension. Schema is defined in `backend/app/models/` and
created only through Alembic migrations in `backend/migrations/`. 43 tables (migration 0003 added `email_tokens`).

| Source registry | sources, source_versions, source_reviews |

| Hadith | hadith_collections, hadith_records, hadith_gradings |

## Rules the database enforces itself

These are CHECK constraints and unique indexes, so no application bug can bypass them.

- **Licensing:** a source can be `approved` only if its licence is verified (`license_verified_at`),
  `commercial_use = 'allowed'`, and `rights_holder`, `license_name` and verified content are set.
  Rights default to `unknown`, which can never be approved.
- **Sourced duas** must have a reference and a source version. Editorial duas are labelled as such.
- **Citations** point at exactly one real record (chunk, verse, hadith or dua) via foreign key,
  so a citation cannot be an invented string.
- **Bookmarks** have exactly one target and cannot be duplicated per user.
- **One correct option** per quiz question at most.
- **Canonical Quran ids:** surah number 1 to 114; one verse per (surah, verse, source version).
- **Hadith gradings** are stored per grader, so differing assessments sit side by side.
- **Idempotent ingestion:** the same file (SHA-256) cannot be registered twice for a source, and the
  same text cannot be chunked twice in one document.
- **Deletion:** user-owned data is deleted with the user. Source and content records use RESTRICT,
  so a source that has content cannot be hard-deleted (archive it instead).

## Embeddings

`chunk_embeddings.embedding` is `vector(1024)` with an HNSW cosine index. Each row records the
embedding model and index version. Changing to a model with a different size needs a migration.
Keyword search uses a generated `tsvector` column on `chunks` with a GIN index.

## Required database privilege

`CREATE EXTENSION vector` needs a privileged user. The first migration runs it. On Docker the
app user is a superuser, so it just works. On managed PostgreSQL (AWS RDS, Azure) a DBA must
allow the extension first. Verify the service supports a recent pgvector before choosing it.

## Migrations

```bash
alembic upgrade head      # apply
alembic downgrade base    # remove everything (development only)
```

Note on Alembic: autogenerate writes each enum CHECK twice with the same name. In migration 0001
the duplicates were removed and `create_constraint=False` is used inside the column type. Review
future autogenerated migrations for this. A test fails if the models and migrations drift apart.

## Migration 0002: source review statuses and per-use permissions

`sources.approval_status` now uses its own value set (`draft, candidate, pending_permission, restricted,
under_review, approved, rejected, archived`); quizzes and learning paths keep the original five.
New columns `storage_permission`, `indexing_permission`, `rag_permission` (default `unknown`). A source can
be `approved` only if commercial use and all three are `allowed`, `license_verified_at`, `license_name` and
`rights_holder` are set, and the content is verified. When writing migrations by hand, wrap constraint names
in `op.f(...)`; otherwise the naming convention is applied a second time and the name will not match.
